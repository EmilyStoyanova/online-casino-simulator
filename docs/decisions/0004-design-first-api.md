# ADR-0004: Design-first REST API and layered module packages

- **Status:** Accepted
- **Date:** 2026-10-29

## Context

The API will grow quickly (authentication, profile, wallet, roulette, learning, administration),
and the frontend team depends on stable request/response formats. With code-first documentation,
the specification only describes whatever the code happens to do. Contract changes are not reviewed
on their own and can break the frontend unnoticed.

The mentorship also asked for a conventional, easy-to-navigate layered package structure
(`controller`, `service`, `repository`, `entity`, `dto`, `config`, `exception`).

## Decision

1. **Design-first API.** `backend/src/main/resources/static/openapi.yaml` (OpenAPI 3.1) is the source
   of truth for the HTTP API. Every API change starts with a reviewed change to this file.
2. **Contract verification without code generation.** Controllers and DTO records are written by
   hand. Two automated checks keep them aligned with the contract:
   - `OpenApiContractIT` compares the specification springdoc generates from the code
     (`/v3/api-docs`) with the contract for all `/api/**` paths: paths, methods, operation ids,
     tags, parameters, request bodies, status codes, media types and schemas, including `required`,
     `enum`, `format` and nullability.
   - Actual responses (including `503` and `500`) are validated against the contract schemas, and
     undocumented properties are rejected.
   The checks use the swagger-core models already shipped with springdoc, so no new dependency is
   needed.
3. **Swagger UI** shows the contract by default (`/openapi.yaml`) and the generated implementation
   view as a second definition.
4. **Layered packages inside each module** (`com.casino.<module>.controller/service/repository/entity/dto/…`).
   The modular monolith from [ADR-0001](0001-modular-monolith.md) is kept, and only the layer names
   inside a module change.

## Alternatives considered

- **OpenAPI Generator (Maven plugin, 7.26 supports Spring Boot 4 / Jackson 3)**, generating
  controller interfaces and DTOs. This gives compile-time enforcement, but it adds a build plugin
  and generated, mutable DTO classes outside the `dto` packages. It can be adopted later without
  changing the contract.
- **Global layer packages** (`com.casino.controller`, `com.casino.service`, …). Rejected: they would
  erase the module boundaries agreed in ADR-0001.

## Consequences

- ✅ The contract is reviewed like code, and drift fails the build.
- ✅ The frontend can rely on the documented formats. TypeScript types could later be generated
  from the same file.
- ⚠️ Writing both the contract and the DTO is some duplication; the contract test makes it safe.
- ⚠️ Actuator endpoints are documented in the contract but not generated by springdoc. They are
  verified by runtime response checks instead of the structural comparison.
- ⚠️ The Week 2 plan (`docs/plans/week-02.md`) and its ArchUnit rules must use the new layer names.
